## القرار وأسبابه

القارئ يقبل **نسخة V1 Operator محفوظة وخاملة موجودة مسبقًا**، مع بصمة manifest مستقلة وربط خلفي موثوق للشركة/المصدر/الملف الشخصي. يعيد استعمال verifyV1Backup القائمة للتحقق من الأدلة واللقطات والأصناف والتدقيق، ثم يبني ملاحظة ثابتة في الذاكرة تقرؤها Application Service القائمة.

استُبعد initialize لأنه قد ينفذ تهيئة أو migration أو recovery. واستُبعد inspectV1State من هذا المسار لأنه يفتح معاملة تحكم. لم نضف وضع قراءة شكليًا إلى التخزين، ولم نغيّر أي عقد عام أو حارس V1 أو مخطط SQLite. لا ينشئ القارئ نسخة احتياطية أو يصلح الملفات.

«أحدث لقطة» تعني أحدث التقاط **داخل النسخة المختارة**؛ لا أحدث حالة نشطة أو مخزون ERP الحالي. هذا قيد نطاق مقصود يحتاج مراجعة قبل التكامل النهائي. لا اسم وحدات مفترض لرمز1، ولا تحويل صرف استهلاكي إلى مبيعات أو اعتماد نهائي للقيود المحاسبية.

الأربعة متجاوزة على Windows في اختبارات POSIX/روابط موجودة أصلًا؛ ليست نجاحًا. اختبار junction الجديد في D3 نُفذ ونجح دون تغيير صلاحيات.

اختُبرت سلامة أسماء الملفات/المجلدات والبصمات والأحجام وأوقات mtime/ctime/birthtime، وغياب إنشاء sidecars/ملفات تهيئة، في النجاح والفشل. access-time الذي قد يديره نظام الملفات مستثنى؛ هذه ليست مراقبة kernel لكل syscall أو إثباتًا لكل metadata. فُحصت مقابض القراءة r وSQLite Buffer/readonly؛ لا اتصال SQLite بملف المصدر في القارئ الجديد.

ثبت الصفر عبر استيراد ونسخ اصطناعيين قائمين ثم قراءة محفوظة، والفرق بين الغياب والصفر، ورفض كمية V1 مفقودة أو مزورة حتى بعد إعادة حساب manifest، وغياب تدقيق الإكمال أو دليل المصدر، والمخطط المتعارض، وWAL/SHM/journal الفارغة وغير الفارغة، والنشر المعلّق، وفشل الوصول، وتغير المصدر، وعزل المراجع والصفحات بين المصادر. الرد المتأخر بعد close لا ينشر أرقامًا.

الاختبارات المحلية استعملت dist تطوير موجودة مسبقًا مع بصماتها؛ **ليست بناء main نظيفًا**. أُضيف workflow مستقل يبني checkout طلب المراجعة على Windows وUbuntu ثم يعيد اختبارات D3. نتيجة CI تُقرأ من الطلب/الأدلة اللاحقة، ولا تُستنتج من هذا الجدول.
