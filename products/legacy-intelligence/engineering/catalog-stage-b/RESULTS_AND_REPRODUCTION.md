## ما أثبتته APIs الموجودة

1. حفظ A/B ثم A المعدّل/B/C من خلال ImportOrchestrator وSqliteLocalStore وSqliteAuditSink الفعلية، مع ثبات `pk-A` وتغير name/SKU.
2. بقاء قارئ baseline المثبت على A/B بعد الاستيراد الثاني؛ وبعد إغلاق التخزين وإعادة فتحه بقيت الحالة الحالية وثبت وجود الصفوف التاريخية.
3. إعادة اللقطة نفسها بعد الفتح أعادت checkpoint نفسه. إعادة لقطة قديمة معروفة لم تُرجع current إلى الماضي. التدقيق يسجل محاولات الاستيراد، لا اللقطات الفريدة فقط.
4. إعادة snapshot ID نفسه بمحتوى مختلف أعادت `DATA_INTEGRITY_CONFLICT` دون تغيير baseline.
5. غياب B في اللقطة التالية جعل المجموعة الحالية A/C، مع بقاء B تاريخيًا؛ لم يُنشأ deleted/tombstone أو رصيد صفري، ولم تُحمل قيم قديمة إلى المجموعة الجديدة.
6. مصدران لهما المفاتيح والرموز وأرقام اللقطات نفسها بقيا منفصلين عند استعمال namespaces منفصلة. SKU واحد بمفتاحين مختلفين لم يدمج المنتجين.
7. المفتاح المكرر داخل لقطة واحدة رُفض بالحارس القائم `DUPLICATE_ENTITY_ID` دون commit.

قراءات current وpinned reader وقائمة checkpoints استخدمت APIs العامة. فحص الصفوف التاريخية بعد إعادة الفتح استخدم SELECT عبر اتصال read-only إلى SQLite الاصطناعية فقط. **لم تُضف API عامة لقراءة لقطة تاريخية برقمها.** لا يوجد تغيير مباشر في SQL لتصنيع نتائج أو تجاوز الاستيراد.

## ما أثبته harness فقط وما كشفه من نقص

النموذج المرجعي رفض هوية/نطاق/إصدار mapping أو ترتيبًا غير مطابق، وملفًا ناقصًا أعيد حساب count/hash الخاصين به، بمقارنته بشاهد اصطناعي مستقل مأخوذ من fixture الكامل قبل إفساده. غياب الشاهد أو صفر غامض رُفضا؛ صفر مؤكد في fixture كامل قُبل. هذه أمثلة للعقد، وليست parser آمنة لملف مجهول أو إثباتًا لهوية ERP فعلية.

اختبارات الفجوة استعملت APIs الحالية مباشرة وأثبتت أنها تقبل جزءًا صالحًا شكليًا أو مجموعة فارغة دون شاهد اكتمال، وأن تعيين شركة أخرى إلى namespace الشركة الأولى قد يغيّر current. هذا **حد قائم غير معالج**، وليس نجاح عزل تشغيلـي. منع بوابة harness لاستدعاء importer بعد الرفض لا يعني أن المحرك بات يرفض ذلك بنفسه.

لقطتان بهويتين وزمنين جديدين لهما صفوف أعمال متساوية تبقيان مشاهدتين مستقلتين. لا يصح وصف ذلك بحدث تغيير أعمال أو deduplication دلالي.

## إعادة الإنتاج

المصدر القابل للمراجعة: [نتائج المنتج وتعليمات التشغيل](https://github.com/elias-mujally/dbl-legacy-intelligence/blob/ecba3c2129488fa98bf88355df560bd2f5becf8f/docs/contracts/CATALOG_STAGE_B_RESULTS.md). بعد إعداد التطوير المعتاد المصرح به مسبقًا، من جذر المنتج وبالتبعيات الموجودة:

```text
node node_modules/vitest/vitest.mjs run packages/import-orchestrator/test/catalog-stage-b/full-catalog-capture.test.ts --maxWorkers=1
node node_modules/typescript/bin/tsc --noEmit -p packages/import-orchestrator/tsconfig.json
```

ملفات الاختبار تحت `packages/import-orchestrator/test/catalog-stage-b/`، فيكتشفها اختبار الحزمة وفحصها المعتادان دون تعديل package.json أو CI. لا يلزم Preview1 أو ملف اقتناء فعلي أو حساب SQL. لا تضبط متغيرات الأدلة الخاصة ولا تزود ملفات تاريخية لهذه الجولة الاصطناعية.

الـmanifest يسجل SHA-256 للتقارير الأصلية المحتفظ بها محليًا دون نشرها. إعادة التنفيذ تنتج أوقاتًا وبصمات تقارير مختلفة. الأدلة المنشورة هي الشيفرة الاصطناعية والعقد والأعداد والحدود؛ CI له نتيجة مستقلة يجب قراءتها من PR22 ولا يُستنتج نجاحه من التشغيل المحلي.
