# خطة CA محلية داخل V1 — تصميم تنفيذي للمراجعة

التاريخ:2026-11-02. اختار المالك مسار CA للمختبر، دون تفويض التنفيذ.
الحالة: **DESIGN_SELECTED / MUTATION_NOT_AUTHORIZED**.
لا إنشاء مفاتيح أو شهادات أو مخازن أو ثقة أو حسابات أو تغيير SQL في هذه
المرحلة. لا شهادة أو PFX أو مفتاح أو بصمة تشغيل في GitHub.

## الهدف والحدود

تأهيل التحقق من شهادة SQL لعميل DBL داخل VM نفسها. لا CA على المضيف،
ولا AD CS أو برنامج إضافي أو خدمة أو إنترنت أو منافذ TCP جديدة. يبقى النقل
Shared Memory والتحقق Encrypt=True وTrustServerCertificate=False. لا
تجربة اتصال من موافقة الجرد السابقة؛ كل اختبار SQL يحتاج نطاقه المأذون.

الجهة مخصصة لهذا المختبر وليست بنية ثقة إنتاجية أو توقيع Trusted Catalog
أو توقيع شيفرة PowerShell. إصلاح TLS لا يغيّر Restricted ولا يمنح SELECT.

## تصميم الشهادات المرشح

| الخاصية | CA المختبر | شهادة SQL |
|---|---|---|
| الاسم المقترح | DBL V1 Lab TLS CA 20261102 | اسم جهاز V1 المثبت |
| المفتاح | RSA3072، غير قابل للتصدير | RSA2048، غير قابل للتصدير |
| التوقيع | SHA256 | SHA256، موقعة من CA المحددة |
| الصلاحية المقترحة | سنة واحدة | 90 يومًا، دون تجاوز صلاحية CA |
| Basic Constraints | CA=true وPathLength=0 | CA=false |
| Key Usage | CertSign،CRLSign | DigitalSignature،KeyEncipherment |
| EKU | تقييد server-auth ضمن تصميم السلسلة | Server Authentication فقط |
| Provider | provider محلي متاح ومثبت قبل الإنشاء | Microsoft RSA SChannel Cryptographic Provider،KeySpec=AT_KEYEXCHANGE |
| المخزن | Cert:\LocalMachine\My لحفظ جهة التوقيع | Cert:\LocalMachine\My |

الأطوال والمدد سياسة مختبر مقترحة، وليست قياسًا أو حدًا تسويقيًا. يجب إثبات
دعم provider وخصائص الإصدار المثبت دون تثبيت بديل. لا تجريب فعلي للمفتاح
أثناء فحص الاستعداد. التحقق من KeySpec في الشهادة الجديدة فقط عند الإنشاء
المأذون؛ لا قراءة مفاتيح شهادات أخرى. استخدام KeySpec=Signature للخادم مرفوض.

اسم الخادم/SAN: جهاز V1 المحلي المؤكد فقط، وlocalhost إذا كان اسم اتصال
مطلوبًا فعلًا. لا اختراع FQDN أو عنوان IP أو wildcard، ولا تعويض mismatch
بتعطيل التحقق. تُثبت صيغة Data Source المحلية قبل الربط؛ انتقال من . إلى
الاسم المحلي الصريح يحتاج مراجعة helper/pin وفحصًا، وليس TCP fallback.

## مخزن الثقة وحماية المفاتيح

المرشح الأقل توسعًا: نسخة عامة فقط من CA في Cert:\CurrentUser\Root لحساب
DBL العادي داخل الضيف. يجب إثبات أن SID المستهدف هو نفس حساب التطبيق؛
لا تركيبها في ملف مستخدم إدارية مختلفة. لا LocalMachine\Root أو TrustedPeople
أو مخزن ثقة المضيف. تضاف الشهادة ببصمتها المراجعة، لا بأول Subject مطابق.

دعم هذا النطاق بواسطة System.Data.SqlClient/Schannel في هذه البيئة **غير
مقاس بعد**. توثق Microsoft اعتماد العميل على trusted-root store؛ لا نجزم
بأن نطاق CurrentUser يكفي لكل provider. إن فشل العميل لا نوسّع إلى
LocalMachine\Root تلقائيًا؛ تصبح توسعة النطاق قرارًا منفصلًا بموافقة جديدة.

إضافة CA توسّع الثقة لهوية المستخدم، فلا توصف بأنها بلا أثر أمني. يبقى
مفتاح CA داخل VM، غير قابل للتصدير، مع صلاحية توقيع مقيدة للمسؤول المخول
والنظام فقط؛ لا حاجة لخدمة SQL للوصول إلى مفتاح CA. مفتاح SQL يحصل على
الحد اللازم لحساب الخدمة. الصلاحيات الافتراضية ليست إثباتًا؛ تسجل ACL
للوعاءين وتراجع قبل الإنشاء/الربط. إن احتاجت تعديلًا يُعرض ACE/SID/rights
والمسار الفعلي وخطة إعادة ACL أولًا؛ لا FullControl واسعة أو إصلاح تلقائي.

ملاحظة عزل مهمة: السماح لـSYSTEM على مفتاح CA لا يعزل المفتاح عن خدمة
تعمل بهذه الهوية. كما أن non-exportable لا يمنع استخدام المفتاح للتوقيع ممن يملك
صلاحية استعماله. لذلك لا ندعي عزل CA عن SQL أو عن مسؤول الجهاز؛ هذه خطة
مختبر محدودة، وتغيير حساب الخدمة أو وسيلة عزل أقوى قرار مستقل غير مفوض.
[Microsoft: صلاحيات LocalSystem](https://learn.microsoft.com/en-us/windows/win32/services/localsystem-account).

لا PFX أو private-key export. يمكن حفظ public DER فقط لمراجعة البصمة داخل
مجلد إيصال خاص جديد في مستندات المالك داخل V1. لا AIA/CDP شبكية؛ تبقى
خطة مختبر محدودة العمر، دون ادعاء خدمة revocation أو بنية CA إنتاجية.
حماية مفتاح CA والضبط الزمني والسحب/التجديد حدود تشغيل معلنة.

## الشرائح وترتيب التفويض

### R0 — فحص استعداد بالقراءة فقط، يحتاج موافقة منفصلة

الغرض تثبيت المعلومات اللازمة لتجهيز أوامر تطبيق وعودة دقيقة، لا تكرار
السجل أو اتصال TLS. القيم المطلوبة: إصدار sqlservr.exe المحلي من ImagePath
لخدمة YSEDU فقط؛ حالة الخدمة؛ اسم المثيل من Registry32؛ قيم Certificate
وForceEncryption الحالية؛ SID الحساب المستهدف ومقارنته بهوية التطبيق؛
توفر PKI cmdlets ومعاملاتها وprovider المقترح؛ الوقت UTC وسياسات التنفيذ؛
وجود أسماء CA/SQL المقترحة في المخازن المحددة (public metadata فقط).

لا SQL/ERRORLOG/أرشيف/private-key handles/chain-build/شبكة أو قراءة شركات.
لا سكربت تطبيقي يُنفذ قبل R0. أي رفض وصول يوقفها دون عرض أو مسار بديل.
المساعد المستقبلي يحفظ تقريرًا خاصًا جديدًا ويخرج ملخص استعداد محدودًا؛
تفاصيل الهوية والمخازن والمسارات والبصمات لا تُرفع إلى GitHub أو CI.

### R1 — دليل استعادة ونافذة صيانة، قبل أي تغيير أمني

وسيلة استعادة مناسبة للحالة الحالية تُثبت مستقلًا. النسخة التاريخية السابقة
لحركة T02 لا تمثل تلقائيًا حالة ERP الحالية. لا BACKUP/RESTORE أو checkpoint
أو تصدير VHDX أو تنظيف دون مراجعة المسارات والحجم والأثر وموافقة منفصلة.
لا نعيد إنشاء المختبر. لا كتابة ERP متزامنة ولا إيقاف مفاجئ للعمليات.

### T1 — تجهيز حزمة تطبيق وعودة ثم طلب موافقة تنفيذية محددة

بعد R0/R1: تعرض قائمة الأوامر والمخازن والملفات والـACL المطلوبة وحالة
الربط السابقة وبصمة كل ملف مساعد، مع dry-run لا ينشئ مفاتيح أو شهادات.
يكون الوضع الافتراضي توقفًا، ولا إجراء كتابة لمجرد اختيار مسار التصميم.

يجب أن تتضمن الموافقة صراحة: إنشاء المفتاحين والشهادتين، trust scope المحدد،
ربط YSEDU فقط، أي key ACL محددة، نافذة restart، ومن يفعل ذلك، وحدود العودة.
لا تستخدم أداة Computer Use لإدارة UAC أو تطبيق أمن Windows؛ ينفذ المالك
الخطوة الإدارية بنفسه عند اعتمادها، ولا يُشغّل DBL من الجلسة المرتفعة.

### T2 — تطبيق مرشح واحد في نافذة الصيانة، غير مأذون الآن

1. إعادة مطابقة baseline الإعداد/الهوية/الوقت وتوفر الاستعادة. لا كتابة قبلها.
2. إنشاء CA وشهادة خادم واحدة بالأسماء والخصائص المعتمدة، وتسجيل البصمات
   فورًا. لا إعادة إذا وُجد اسم/وعاء/شهادة من محاولة سابقة؛ تحفظ وتراجع.
3. التحقق من البنية والاسم والـEKU وKeySpec والتواريخ وحماية المفتاح ونطاق
   الثقة. لا private-key export، ولا ثقة في cert مجهولة ظهرت بالسجل.
4. ربط شهادة الخادم المعينة بالطريقة المدعومة للإصدار وأداة الإعداد المتاحة.
   لا تعديل ForceEncryption أو البروتوكولات أو المصادقة أو تسجيل القارئ.
5. إعادة YSEDU مرة واحدة فقط بعد موافقة نافذة الصيانة؛ إن فشل البدء تتوقف
   المزامنة ولا تعاد الخدمة دوريًا أو يشغل ERP لإخفاء الفشل.

لأن SQL قد يختار شهادة صالحة تلقائيًا عند إعادة خدمة لاحقة، لا تُترك شهادة
خادم جديدة مؤهلة في My كمرحلة نصف مكتملة دون خطة عودة ومعرفة المالك.

### T3 — قبول عميل صارم ثم إغلاق TLS فقط

من حساب DBL العادي: محاولة اتصال metadata واحدة مقيّدة بهوية شركة الاختبار
والمثيل والنقل. Encrypt=True،TrustServerCertificate=False،مهل محددة ولا retry
أو alternate transport. لا صفوف أصناف أو حركات أو بيانات مالية أو استعلامات
خارج النطاق المراجع. تأكيد اسم الخادم/القاعدة/الإصدار وهوية الجلسة الفعلية.

PASS يعني قبول عميل صارم للهوية والسلسلة في هذه الجلسة مع حدود النقل
موثقة. ليس نجاح X509Chain وحده، ولا ظهور شهادة/سطر بدء، ولا encrypt_option
وحدها. Shared Memory لا يعطي تلقائيًا دليل تشفير شبكي؛ لا تدّعى مقاومة
MITM أو قياس TLS على الشبكة. أي name/chain/expiry/provider خطأ يوقف القبول
ولا يتبعه توسيع مخزن أو تعطيل تحقق. توقيع .ps1 لا يصلح Restricted وحده.

## العودة عند الفشل

العودة عملية محددة ضمن الموافقة التنفيذية، لا تنظيف عام. تحفظ كل الإيصالات
والإخفاقات. لا حذف لشهادة أو ملف أو قيمة سابقة من الجهاز.

- حفظ الربط السابق ووجود القيمة ونوعها، وحالة ForceEncryption دون تغيير،
  وقائمة البصمات والـACL ذات الصلة قبل التطبيق.
- إعادة الربط السابق وحده لا تكفي إذا بقيت شهادة جديدة مؤهلة للاختيار
  التلقائي. يجب إيقاف أهليتها ضمن خطوة عودة مراجعة ومصرح بها، تستهدف فقط
  الشهادة المُنشأة في هذه المحاولة ببصمتها؛ لا البحث بالاسم والحذف العام.
- إزالة trust anchor الجديد فقط إن كان أضيف في هذه المحاولة، وفق الإذن
  الصريح. لا إزالة أصل كان موجودًا قبلها أو CA مشتركة.
- إعادة ACL المعدلة إلى نسخة baseline بدقة، ثم إعادة خدمة واحدة ضمن نافذة
  العودة المعتمدة فقط. لا محاولات متكررة إن فشلت العودة؛ يتدخل المسؤول.
- إن تعذرت عودة سليمة، تبقى التطبيقات متوقفة عن المزامنة ويُستخدم مسار
  الاستعادة المستقل المعتمد؛ لا RESTORE أو إعادة VM تلقائيًا من هذا التصميم.

تُحسم طريقة إخراج الشهادة الجديدة من أهلية SQL دون فقد مفتاح/إيصال في
أداة العودة بعد R0. لا نعد بخطة عودة منفذة أو ذرية لمتاجر الشهادات والخدمة.

## معايير الخروج والبوابات التالية

R0: معلومات كاملة ضمن النطاق أو عائق صريح؛ لا نقص يُحسب PASS.
R1: استعادة مناسبة ونافذة صيانة مقبولتان، مع أدلتهما الخاصة.
T1: سكربت تطبيق/عودة مراجع وبصماته وdry-run وموافقة تنفيذية صريحة.
T2/T3: دليل خدمة وعميل صارم من الحساب الصحيح دون تخفيف، أو فشل محفوظ.

بعد ذلك فقط تُراجع سياسة المساعد وحساب SQL ذي SELECT لعمودين وDPAPI
والاستخراج المتسق والمزامنة الحالية. لا غلق Trusted Catalog أو هوية i_code
عبر الزمن أو المخزون الحالي أو الصنف السادس أو A16/Narrator/Windows/الإنتاج.
