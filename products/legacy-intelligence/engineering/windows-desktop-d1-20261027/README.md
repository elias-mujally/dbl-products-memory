# Desktop D1 — نتائج التجربة التقنية

2026-10-27 · **PARTIAL_D1_NATIVE_IPC_PASS_TARGET_RESOURCE_BUDGET_OPEN**

اختار المالك الاتجاه الأول في D0 ووافق على D1 فقط. التجربة معزولة في experiments/desktop-d1، خارج workspaces، دون تعديل المحرك أو العقود أو المخطط أو lockfile أو Preview1، ودون ERP أو قبول Catalog أو شروع في D2.

## المثبت فعليًا

- نجحت اختبارات العامل المستقل **18/18** بلا إخفاق أو تجاوز: Node22.23.2 وABI127 وSQLite3.51.3، وعينة SQLite اصطناعية جديدة من خمسة أصناف عربية بلا أرصدة أو أسعار، عبر Application Service العام. اختُبرت مصافحة خاطئة وصفحات مثبتة ورفض الرموز والحدود والعمليات غير المسموحة. إعادة الاختبارات لا تضاعف عدد الحالات.
- نجح التشغيل الأصلي مرة من جلسة المالك العادية غير المرتفعة، التي يفحصها المشغل ويرفض دور Administrator. اجتاز **17/17** فحصًا أصليًا، منها **14 حالة IPC سلبية**. وصل renderer/preload إلى Node المستقل وSQLite، ورفض حقول path/SQL والمراجع المزورة والحدود الخاطئة وcursor المزور وscope المغلق وwebContents غريبًا.
- بقي sandbox وcontextIsolation وwebSecurity مفعّلة، وNode وgeneric IPC غير متاحين للـrenderer. لا منح ACL أو تعطيل حماية أو رفع صلاحيات أو تغيير مكان SDK. القيود ليست حاجزًا أمنيًا أمام مالك محلي معادٍ يستطيع تغيير ملفات البرنامج.
- التُقطت صورة عربية فعلية وفُحصت بصريًا: شاشة تقنية توضح الاصطناعية وعدم تأهيل ERP، وتعرض جاهزية المحرك ونتيجة قراءة خمسة أصناف. ليست واجهة D2 ولا قبولًا بشريًا؛ qualification استخدم نافذة اختبار مخفية والتقاطًا آليًا.
- بقيت بصمات14 ملف منتج مرجعي سابق دون تغيير. نُسخ build قائم وخمسة حزم DBL واعتماديات native إلى runtime جديد؛ لا تثبيت أو build للمحرك في هذه المهمة.

## القياسات وحدود النجاح

رُصدت جاهزية عند نحو901ms في تشغيل واحد على مضيف تطوير نحو32GiB. مجموع Electron working sets كان387588KiB، ومجموع حقول peakWorkingSet كان392556KiB، وRSS العامل42090496 بايت. ليست هذه قياسات خمول أو ذروة مجمعة متزامنة أو p95، ولا اختبار الجهاز المستهدف4GiB/2vCPU أو عشر تشغيلات. **بوابة ميزانية D1 ما زالت مفتوحة**؛ لا نعتمد D1 كاملًا ولا نبدأ D2 تلقائيًا.

تبقى أيضًا تجربة build نظيف من main، وWindows نظيف مدعوم، والقبول البشري، وDefender/الأصالة والتوزيع والتوقيع وخصوصية ACL غير مؤهلة لهذا الغلاف. لا تحميل شبكة مقاسًا بالحزم، ولا قراءة ERP، ولا ادعاء جاهزية إنتاجية.

## الفشل والحل المقارن

فشل التشغيل الأول من سياق الوكيل قبل renderer عند فحص Electron لوصول الرمز المقيد إلى icudtl.dat. [شيفرة الإصدار الرسمية](https://github.com/electron/electron/blob/v45.0.0/shell/browser/win/install_dir_access.cc) تطبع تفسير ACL واقتراح icacls ثابتين عند فشل الفحص؛ القراءة المنقحة لأذونات المجلد والملف لم تثبت package ACE الذي تذكره الرسالة. لم ننفذ الاقتراح أو نغير الحماية. نجحت الملفات نفسها من جلسة المالك العادية: المثبت اختلاف النتيجة باختلاف سياق التنفيذ، وليس السبب الدقيق للرمز أو ACE. لا نعيد اختبار السياق المرفوض ولا نحتاج تعديل ACL للمسار الناجح.

فشل تنزيل PowerShell أولًا بخطأ TLS، ونجح Node HTTPS مع تحقق الشهادة القياسي بعد منح إذن شبكة للأداة، دون تعطيل TLS أو تغيير trust. Electron45.0.0 x64 من الإصدار الرسمي، وبصمته مطابقة SHASUMS256 الرسمية؛ SDK التنفيذي NotSigned، فلا يعتبر تطبيق DBL موقعًا. تفاصيل قفل الملفات في ARTIFACTS.json؛ binaries وSQLite والإعدادات والمسارات الشخصية خارج GitHub.

## إعادة الإنتاج والخطوة التالية

راجع README في تجربة المنتج: تهيئة runtime جديد من build معتمد موجود، والتحقق من manifest، وتشغيل18 اختبارًا بالعامل المستقل، ثم المشغل الأصلي مرة من جلسة عادية مع sandbox. لا بديل SQL عام أو اختيار ملف حالة قائم، ولا استيراد أو اتصال مصدر. يُحفظ الفشل دون تنظيف أو إصلاح تلقائي.

الخطوة المقترحة قبل D2: قرار مستقل بشأن بيئة Windows مدعومة4GiB/2vCPU ومرخصة، ثم عشر تشغيلات وقياس p95 والتفاعل والصفحات والخمول والذروة حسب A16، مع build من main. لا إنشاء VM أو تغيير موارد أو شبكة أو صلاحيات ضمن هذه النتيجة. إذا اختار المالك متابعة تصميم القراءة قبل غلق الأداء، يلزم تسجيل ذلك كقرار صريح لا كاختبار ناجح.
