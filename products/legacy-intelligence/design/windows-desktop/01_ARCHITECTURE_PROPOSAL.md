# Desktop Architecture Decision Proposal

حالة القرار: **مقترح للمؤسس، غير معتمد** ·2026-10-25 · [الفهرس](README.md).

## المشكلة ومعايير القرار

المحرك TypeScript/Node22 ويستخدم better-sqlite3/native ABI127 في حزمة Windows المؤهلة. المشغّل يقدم أوامر JSON محددة للملف والحالة والتقرير والتعافي؛ ليس خدمة UI أو API تاريخيًا عامًا. نحتاج واجهة عربية محلية مع بقاء حفظ البيانات والتحقق والترتيب وإعادة الاستيراد في المحرك. إعادة كتابته بلغة أخرى ليست ضمن الاقتراح الأول.

ترتيب المعايير: صحة الربط والعزل، تسليم محلي دون تنزيل اعتماديات للمستخدم، قابلية صيانة فريق المنتج، جودة العربية وإمكانية الوصول، ثم الحجم/الذاكرة. لا قياسات مقارنة ناتجة من تشغيل أطر هنا؛ التوقعات أدناه تحليل معماري مشروط.

Microsoft توصي WinUI3 لتطبيقات Windows الجديدة وتقدّم له نشرًا معتمدًا على runtime أو self-contained. اخترنا WPF كنقطة المقارنة الأصلية العملية بسبب مسار RTL/.NET الواضح؛ ليس ادعاء أن WinUI3 عاجز أو غير مناسب. التحول إلى أي منهما يحتاج قرار مهارات وتجربة نشر. ## التوصية المشروطة

**Electron + React + TypeScript، مع Broker محدود ومحرك خارجي مستقل** هو الترجيح الأول لتقليل مخاطر تغيير المحرك وتسريع فريق TS، ولعرض محلي ثابت دون افتراض WebView2. هذه موازنة للمشروع الحالي، وليست حكمًا بأن Electron أسرع أو أكثر أمانًا من كل بديل.

لا يجوز استخدام runtime Electron لتحميل نسخة better-sqlite3 المؤهلة مباشرة: اختلاف ABI يتطلب إعادة بناء وتأهيل. الإصدار الأول المقترح يستدعي Node22 والمحرك في عملية مستقلة بمدخلات ثابتة؛ يقلل مخاطرة ABI لكنه يزيد حجم الحزمة وتكلفة تحديث مكونين. utilityProcess أو إعادة بناء addon ممكنان لاحقًا، ولا يعدّان المسار المؤهل نفسه.

Tauri يبقى بديلًا ذا معنى إذا أثبتت تجربة محدودة أن إجمالي الغلاف+المحرك+خيار WebView2 يحقق هدفًا مهمًا للحجم/الذاكرة دون تعقيد نشر غير مقبول. WPF يُرجح إذا أصبح فريق C#/Windows UI وخبرة الوصول الأصلي أهم من مشاركة TS. لا نختار إطارًا لمجرد رقم تسويقي للحجم.

## شكل البناء المقترح

واجهة React محلية → preload facade مقيّد → broker → jobs مؤقتة بمحرك Node مستقل → تخزين DBL الحالي. لا HTTP محلي ولا منفذ SQL ولا متصفح إنترنت ولا أوامر عامة. تعديلات المستقبل في غلاف/مهايئ Desktop منفصل؛ لا تعديل Preview1 أو بياناته أو صيغة SQLite تلقائيًا. التفاصيل والأخطار في [حدود الربط](05_ENGINE_AND_SECURITY.md).

التوزيع الأول المقترح حزمة تقييم خاصة ذات إصدار و manifest، قد تكون مجلدًا محمولًا؛ المثبت ليس شرطًا. التوقيع وخيار per-user installer/MSIX يقرران بعد تجربة التوزيع. الأصول والخطوط والأيقونات محلية. تحديث يدوي موثق وموقع/موثوق بعد موافقة المستخدم، مع نسخة حالة متحققة؛ لا auto-update أو telemetry افتراضيًا.

## تجربة الحسم بعد الموافقة فقط

تجربة Electron واحدة أولًا: نافذة عربية sandboxed، أصول محلية، تحقق حزمة ومحرك ثم read/status على حالة اصطناعية منفصلة. لا استيراد/هجرة بيانات أصلية. يجب إثبات تشغيل Node الصحيح و binding الحالي، وعقد JSON محدود، وإغلاق الطفل، وفشل محاولات path/IPC غير المسموحة. قياس الحزمة كاملة والعمليات كلها: working set/private bytes والذروة، تشغيل بارد/دافئ، doctor/status/import اصطناعي و readback، DPI والعربية. أهداف أولية للنقاش: ظهور واجهة قابلة للاستخدام خلال 3 ثوانٍ ونتيجة حالة العينة خلال 5 ثوانٍ على الجهاز المرجعي المتفق عليه؛ ليست نتائج حالية أو ضمانات.

إذا تجاوزت الكلفة حدود المؤسس المتفق عليها، نطلب تجربة Tauri بنفس البيانات والأجهزة وطريقة جمع القياس؛ لا نفترض مكسبه. لا تنفيذ تجربتين أو تنزيل SDK ضمن هذه المرحلة. بعد القياس يعتمد المؤسس ADR نهائيًا بإصدارات محددة ومتطلبات دعم وتوزيع وميزانية ذاكرة واقعية.
